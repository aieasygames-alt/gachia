# 游戏内容更新工作台：产品方案、架构与风险防线

> 项目：Gachia
> 日期：2026-10-10（Asia/Shanghai）
> 状态：实施中；崩坏3手动证据、任务、草案审核与本地预览切片已实现，三个总体阶段均未完整验收
> 任务状态核对：2026-10-13（决定见16.6，收口总览见16.91，固定输入回归见16.92；此前任务表为历史观察；未提交、未部署）
> 部署形态：本机运行的管理工具，不属于公开网站功能

## 1. 项目背景

随着站点游戏数量增加，逐个通过聊天安排资料收集、开发、审计和发布，带来重复沟通、更新滞后、状态分散和发布风险。

绝区零、明日方舟：终末地、鸣潮、崩坏3的更新过程中暴露了以下问题：

- 官方事实、历史资料、实时活动与玩家讨论容易混淆。
- 旧角色的新装备可能被误写为新角色，装备触发条件可能被遗漏。
- 详情页已有内容，但列表入口仍为 Coming Soon 或返回 404。
- 多语言、公共数据镜像、搜索索引和 sitemap 可能不同步。
- 页面返回 200，但可能缺少 H1，或交互没有真正完成验证。
- 主站 Worker 包体可能超限，内容增长不能脱离部署预算。
- 多 Worker、CI 与本地发布并行时，难以准确判断实际线上版本。
- 取消流水线时，生产发布可能已经完成，取消不等于回滚。

工作台应整合现有能力，将重复操作程序化，将高风险判断保留为明确审批。

## 2. 目标与设计原则

### 2.1 产品目标

用户能在同一个本地界面中：

1. 查看所有游戏的信息更新与来源健康状态。
2. 理解哪些内容值得更新、为什么更新、依据是什么。
3. 结合项目已有内容生成边界清晰的单游戏任务包。
4. 审核草案、页面预览、实际代码差异及验证结果。
5. 批准符合门禁的发布，并查看真实部署与线上验收结果。
6. 在失败、断网、休眠或部分发布后恢复任务，而非从头重复操作。

### 2.2 核心原则

- **按游戏管理内容，按 Worker 管理发布，按证据管理事实，按验收结果判定完成。**
- 自动发现与准备，不等于自动批准或自动上线。
- 一个游戏形成一个完整内容批次，避免不同游戏的业务更新混杂提交。
- 同一 Worker 的生产发布串行，内容批次独立不代表部署产物独立。
- 事实核验不能被“以官方为准”的免责声明替代。
- 发布的提交和产物必须与审核对象一致。
- 外部资料是不可信输入，不能成为终端或生产指令。
- 确定性步骤由程序执行，AI 负责分析和受约束的内容开发。
- 第一版统一正常发布通道，应急直发不得与 CI 无协调并行。

## 3. 范围与非目标

### 3.1 首批覆盖

- 崩坏3：用于跑通端到端流程。
- 绝区零、明日方舟：终末地、鸣潮：接入同一任务体系。
- 其他游戏通过来源配置、内容适配器和验证规则逐步接入。

### 3.2 第一版包含

- 官方来源采集、手动导入讨论、去重及来源健康检查。
- 事实证据记录、内容索引、更新建议与单游戏任务包。
- 隔离工作区、受约束的 AI 草案、差异审核与页面预览。
- 测试、构建、包体、数据与 SEO 门禁。
- 多 Worker 影响分析、人工批准发布及专项线上验收。
- 任务日志、失败恢复、版本记录和回滚计划。

### 3.3 第一版不包含

- 无人审核自动生产发布。
- 绕过登录、反爬或平台访问限制的采集。
- 所有社交平台的完整覆盖或无依据的热度统计。
- AI 自由执行任意部署命令。
- 自动修改 Router、数据库、权限和 CI 门禁。
- 复杂多人权限系统与桌面安装包。
- 自动将玩家观点转为官方事实、强度排行或抽取结论。

## 4. 用户工作流与界面

### 4.1 日常流程

扫描所有游戏 → 查看更新建议 → 选择单游戏任务包 → 生成草案 → 审核差异与预览 → 通过验证 → 批准发布 → 线上验收。

多个游戏可以同时进入采集和草案阶段，但同一 Worker 的发布必须排队。

### 4.2 主要界面

| 界面 | 必须回答的问题 |
|---|---|
| 游戏总览 | 哪些游戏需要处理、为什么、紧急程度与风险是什么？ |
| 来源与情报 | 信息来自哪里，采集是否成功，有哪些冲突或缺失？ |
| 事实审核 | 原文依据、服务器、时间范围、状态和实体是否正确？ |
| 内容任务 | 更新哪些已有页、新建哪些页、哪些内容归档？ |
| 草案审核 | 实际改动是什么，三语是否一致，是否超出范围？ |
| 验证报告 | 哪些门禁通过、失败或跳过，是否可进入发布？ |
| 发布控制台 | 实际包含哪些提交，影响哪些 Worker，当前执行到哪一步？ |
| 线上验收 | 实际线上版本是什么，页面、资源和交互是否通过？ |

游戏卡片显示最后成功采集时间、资料版本与服务器、失联来源、待确认事实、受影响页面、任务阶段和推荐动作。抓取失败不得显示为“没有更新”。

## 5. 信息采集与事实体系

### 5.1 来源管理

每个游戏维护来源档案：官方网站、公告接口、更新日志、官方社交账号、直播资料，以及可合法获取的公开讨论。

对登录或访问受限的平台，使用获准的接口，或提供手动导入链接、正文的入口。不得保证所有平台都可稳定自动抓取。

来源状态至少区分：成功无变化、成功有变化、正文解析失败、访问失败、长时间未成功检查。

### 5.2 证据与去重

采集记录保存原始 URL、正文必要快照、原发布时间、采集时间、语言、服务器范围、内容指纹和解析器版本。

转载、同一公告的不同语言与重复推送应关联到同一个事件，避免重复生成任务。网页编辑时间不得默认视为新事件发布时间。

证据快照仅保存核验所需内容，设置保留期与访问范围；不默认下载或再分发社交图片、个人资料和完整文章。

### 5.3 事实与讨论分离

**事实记录**包括实体、字段、值、出处片段、适用服务器、有效时间、预告/测试/上线/历史状态、核验状态。

**讨论主题**包括平台、采样时间、样本数量、去重方式、问题摘要和选题建议。没有可靠统计时，只能描述为采样问题，不能宣称玩家普遍共识。

重要事实冲突或证据不足时进入待确认，不直接进入正式内容。以下修改默认人工确认：角色身份、日期、奖励资格、概率、数值、配方及影响付费决策的结论。

### 5.4 时效管理

时效内容记录生效时间、结束时间、下次复核时间和到期显示策略。到期可自动标记需复核或历史参考，但不能仅凭日期断言活动已关闭或奖励不可领取。

## 6. 内容索引、规划与开发

### 6.1 项目内容索引

索引角色、武器、材料、攻略、版本档案、下载页、目录与详情、三语覆盖、搜索入口、内链、sitemap、数据镜像及 Worker 归属。

不仅检查详情存在，还要检查用户能否从目录、版本页和搜索真正进入内容。

### 6.2 更新任务包

每个任务包必须声明：

- 目标游戏、服务器、版本和更新目的。
- 已确认事实、待确认事实与证据。
- 更新已有页面、新建页面、归档内容及理由。
- 允许修改的文件范围和禁止触碰的高风险路径。
- 三语、目录、数据镜像、搜索与 sitemap 的联动要求。
- 验收清单、风险、预算与完成标准。

默认优先更新已有页。新建页面需要解释独立搜索意图、增量信息和后续维护安排，避免重复攻略持续膨胀。

### 6.3 隔离开发与审查

草案在独立 Git 工作区产生，保留用户未提交的其他改动。开发基线记录为确定提交，不从混杂工作目录直接构建生产版本。

AI 执行适配器可替换，具体模型服务后续决定。未配置 AI 时，采集、任务管理、验证与发布仍应可用。调用量、重试与费用设置每日及每游戏限额。

实际差异超出允许范围时，任务暂停并请求扩大授权。CI、部署脚本、Worker/Router 配置、数据库迁移、认证、依赖和测试门禁属于保护路径。

### 6.4 单一事实源

日期、版本、实体身份与数值尽量从单一事实源生成到三语页面。公共 JSON、搜索索引和 sitemap 尽量通过生成器产生。

镜像一致性检查比较内容，而不只是判断文件存在。翻译名称尚未核实时明确标注，不冒充正式本地化名称。

## 7. 安全边界与执行权限

| 层级 | 允许 | 禁止 |
|---|---|---|
| 采集与分析 | 读取资料、抽取事实、提出建议 | 执行命令、读取生产凭据、发布 |
| 内容开发 | 在隔离工作区修改授权文件 | 擅自修改权限、CI、Router、数据库与凭据 |
| 发布执行器 | 执行固定、参数化的已批准流程 | 接收网页指令、执行模型生成的任意 shell |

外部文本可能包含提示注入，所有采集资料必须作为数据处理。读取外部信息的模型不应同时持有生产权限。

凭据使用系统安全存储或受保护本机配置，不进入 Git、模型输入、普通日志和导出报告。日志必须脱敏。

本地管理服务仅绑定本机，并实施认证、来源校验、跨站请求防护和发布确认。不能因使用 localhost 就认为任意网页调用是安全的。

## 8. 多 Worker 发布设计

### 8.1 影响分析与发布清单

读取现有部署注册表，不另设一套不一致的 Worker 归属表。

- 主站内容：影响主站 Worker。
- 独立游戏内容：影响对应游戏 Worker。
- 共享包：分析所有使用方，扩大验证范围。
- Router、数据库、权限：进入独立高风险审批。

一个游戏一个提交不等于一个游戏一个部署。发布清单必须列出本次实际包含的已批准提交、完整 Worker 内容范围和依赖变更，防止带入未批准改动。

### 8.2 审批绑定不可变对象

批准记录绑定 Git 提交、差异摘要、构建配置、构建产物标识和目标 Worker。任一变化使批准失效。

优先将通过预发布验证的同一份产物发布到生产；环境绑定差异需要显式记录。如果必须重新构建，重新验证产物并确认批准是否仍适用。

### 8.3 单发布通道与发布锁

第一版优先复用 GitHub 流水线作为正常生产通道。发布锁必须对本地与远端执行器都有效，仅本机 SQLite 锁不足以约束 CI。

同一 Worker 发布串行，后续发布从最新已批准基线构建，禁止旧工作区覆盖较新的线上版本。

本地直发属于应急模式：先处理正在运行的发布任务，再执行明确的目标发布，最后重新核对线上版本。不能静默与 CI 并行。

### 8.4 状态、部分失败与取消

任务状态必须区分：代码已推送、构建通过、预发布通过、生产版本已上传、流量已切换、线上验收通过。

取消任务不等于未发布，也不等于回滚。取消后进入状态待核实，查询每个 Worker 的实际版本和已执行步骤。

多 Worker 发布不是原子事务，应保持新旧版本兼容，按依赖顺序部署，记录每个 Worker 发布前后的版本。部分失败允许停止、重试失败步骤或回滚指定 Worker，不能盲目全量回滚。

数据库变更必须单独制定前向修复与回滚策略，回滚代码不代表回滚数据。

### 8.5 发布门禁

- 测试、类型检查、Lint 和生产构建。
- 数据有效性、源数据与镜像一致性。
- 目录可达性、三语覆盖、内链、搜索和 sitemap。
- Worker 绑定、部署归属、Router 契约与兼容性。
- 包体上限、增长余量及与历史基线的差异。
- 本次受影响页面专项验收与风险审批。

包体超限必须返回失败并阻止发布，而不是仅显示 Wrangler 输出。门禁值依据项目实际限制配置；当前项目以 gzip 3 MiB 为绝对门禁，还需设更低的预警预算。

## 9. 验证与线上验收

### 9.1 三层验收

1. **受影响页面检查：**HTTP、实际正文、唯一 H1、canonical、语言、链接、数据与 sitemap。
2. **关键页面浏览器检查：**渲染、控制台错误、hydration、加载失败、JS/CSS/图片和空白加载态。
3. **关键流程测试：**角色选择、筛选、对比、复制、保存、刷新恢复等实际行为。

返回 200、按钮数量正常或资源可下载，均不能替代完整功能验证。

### 9.2 主域名、缓存与版本核对

同时检查 Worker 原始域名与经 Router 的主域名，核对响应或页面版本标识以及更新内容的实际文本，避免只验证到旧缓存。

验收报告记录观察到的版本、环境、时间、覆盖范围、失败和跳过项目。未经验证的内容不得标记为通过。

### 9.3 验证成本控制

每次发布检查受影响页面及跨 Worker 代表路径；低频全量巡检补充覆盖。设置低并发、请求总量、超时和重试预算，避免生产负载与外部素材站限流。

## 10. 风险登记与对应防线

| 风险 | 可能后果 | 最低防线 |
|---|---|---|
| 官方公告解析错误 | 错误身份、时间和奖励信息上线 | 字段级证据、服务器与状态核验、关键事实审批 |
| 来源失联却显示无更新 | 长期遗漏重要更新 | 来源健康状态、最后成功时间、空窗提醒 |
| 社交采样偏差与重复转载 | 虚假热度和误导选题 | 样本与采样范围披露、去重、事实观点分离 |
| 外部文本提示注入 | 凭据泄露或未授权操作 | 分权执行、资料视为数据、固定发布命令 |
| AI 扩大修改范围或削弱测试 | 越权修改与假通过 | 文件范围约束、保护路径、独立审批 |
| 内容重复和陈旧 | 低质量页面膨胀 | 已有页优先、搜索意图检查、到期复核 |
| 三语与镜像漂移 | 不同页面事实冲突 | 单一事实源、生成式派生、一致性门禁 |
| 未批准内容被整包发布 | 混杂游戏更新进入生产 | 干净基线、明确发布清单与完整差异 |
| 审核后产物变化 | 发布内容不是审核内容 | 审批绑定提交、配置、产物、目标 |
| 本地与 CI 并发发布 | 旧版本覆盖新版本 | 统一通道、跨执行器发布锁 |
| 取消或多 Worker 部分失败 | 误判线上状态 | 步骤级版本记录、状态核对、局部恢复 |
| 200 空壳与交互故障 | 验收假安全 | 正文、浏览器及行为三层验证 |
| 缓存和错误验证域名 | 验收旧版本 | 主域名/Worker 双检查、版本与内容标识 |
| 全量爬取无上限 | 成本、限流和生产压力 | 增量验收、低频全量、请求预算 |
| 休眠、断网、进程退出 | 任务丢失或重复发布 | 持久队列、幂等步骤、启动后状态对账 |
| 磁盘与费用增长 | 本机不可用或预算失控 | 快照与工作区保留策略、容量和调用限额 |
| 本地接口和日志不安全 | 外部网页触发发布、泄露凭据 | 本机绑定、认证、防跨站请求、日志脱敏 |
| 工具升级破坏任务 | 历史记录丢失或无法恢复 | 数据版本化、迁移备份、兼容策略 |
| 素材版权与隐私 | 非授权再分发与个人信息暴露 | 最小必要证据、保留期、来源与使用范围 |

## 11. 技术架构与记录模型

### 11.1 推荐实现

- 本地网页控制台 + Node.js 后台进程，不先制作桌面安装包。
- SQLite 保存来源、证据、任务、审批、执行日志与发布记录。
- Git 工作区隔离内容任务。
- Playwright 验证页面与交互。
- 现有脚本和 CI 承担确定性执行，避免另造发布体系。
- AI 通过适配器接入，凭据与发布执行器隔离。

### 11.2 主要记录对象

| 对象 | 关键字段 |
|---|---|
| GameProfile | 游戏 ID、服务器、来源、内容适配器、部署归属引用 |
| Source / FetchRun | 来源类型、访问策略、最后成功时间、解析器版本、运行结果 |
| Evidence / Fact | 原文片段、URL、时间、语言、实体、范围、核验状态 |
| DiscussionTopic | 采样范围、样本、去重规则、问题与选题 |
| UpdateBatch | 单游戏目标、基线提交、范围、证据、预算与验收要求 |
| Draft / Approval | 实际差异、预览、审批人、提交与产物绑定 |

本次审计的核心结论：

1. 游戏数量不是主要瓶颈；同一游戏在内容、路由、索引、语言和发布层存在多套维护入口，才是复杂度增长的主要来源。
2. 历史 Worker 拆分有包体限制背景，不能未经容量验证就全部合并。
3. 新游戏默认应新增内容包与声明式配置，而不是新增一套 Next 应用、SEO 实现和部署流程。
4. 运营人员应按游戏和内容批次工作，不需要理解底层 Worker 拓扑。
5. 源码、可再生缓存、业务数据、发布证据必须分开管理。磁盘治理重点是减少重复构建副本，不是删除有价值内容。

### 1.1 最终用户体验目标

- 玩家：能迅速找到适用区服、当前版本和可靠来源，不被过期奖励或未翻译页面误导。
- 编辑：一次审核后的事实更新，可以一致地反映到页面、搜索、导航和机器读取入口。
- 维护者：一个发布入口可以看清目标环境、受影响服务、当前版本、候选版本和回滚方式。
- 新游戏接入者：复用成熟模板，完成一个小而完整的内容包，而不是复制整个网站。

## 5. 长期架构与稳定决策

### 5.1 逻辑结构

```text
玩家 / 搜索引擎
        |
统一公共域名与稳定 URL
        |
入口路由（过渡期保留现有 Router）
        +-- 平台：主页、目录、跨游戏搜索、账号与用户状态
        +-- 通用内容：百科、攻略、版本、兑换码、下载说明
        +-- 特殊工具：地图、复杂计算器、专属交互

维护者 --> 统一发布入口 --> 验证 / 预览 / 审批 / 上线核验 / 回滚
                         |
          游戏声明 + 内容清单 + 发布记录
                         |
             版本化内容与不可变静态资源
```

这些是逻辑边界，不是要求新增三组 Worker 或三套数据库。过渡期优先复用现有应用与脚本。

### 5.2 稳定决策记录

| ADR | 决策 | 原因与约束 |
|---|---|---|
| D01 | 保持现有公共 URL，主要形式为 `/{locale}/{gameId}/...` | 不因内部服务迁移改变玩家入口和搜索资产 |
| D02 | 一个页面只有一个逻辑 owner | owner 统一决定正文、canonical、索引、语言与 sitemap |
| D03 | 内容源唯一，镜像与索引可重建 | 防止源/镜像人工双写；先建立生成与消费者契约，再移除旧副本 |
| D04 | 游戏接入与运行时拆分解耦 | 常规游戏复用内容运行时，特殊需求经证据评估后例外拆分 |
| D05 | SEO 正文服务端可用 | 不以客户端异步加载正文代替包体治理 |
| D06 | 发布以不可变版本和核验结果为准 | CI 成功、上传成功、服务切换、业务验收分别记录 |
| D07 | 用户私有数据与公共内容分开 | 公共缓存不得混入会话、收藏、角色进度等个人状态 |
| D08 | 未知影响范围按高风险处理 | 无法分类时完整验证，不为了节省 CI 跳过安全边界 |
| D09 | 先试点再推广，可退回旧 owner | 不同时迁移全部游戏；旧路径和产物保留至观察期结束 |
| D10 | 数据库迁移不是前置条件 | 初期可用版本控制中的 JSON/清单实现，明确需求后才引入新持久存储 |

### 5.3 部署粒度的决策方法

新建独立部署单元需回答：包体或启动预算是否超限、是否有特殊工具依赖、是否需要独立故障隔离、流量是否足以支撑额外维护成本。每项必须有测量或明确业务约束，不能只以“新增游戏”作为理由。

对以下候选进行比较：

1. 保留当前 Worker，统一发布与内容管理。
2. 轻量游戏共享内容部署分组，重工具游戏独立。
3. 在适当付费容量下减少部署分组。

评价公式：月度总成本 = 云服务费用 + CI/构建成本 + 维护工时成本 + 故障与恢复成本。没有账户与工时数据时，只能做情景分析，不可下精确成本结论。

## 6. 核心数据契约

以下为建议模型，不表示仓库已存在同名类型或数据库表。实施时先采用最小字段，不为抽象提前建立复杂框架。

### 6.1 GameManifest：游戏能力与归属

| 字段组 | 建议信息 | 约束 |
|---|---|---|
| 身份 | gameId、显示名、区服关系、负责人、运营等级 | gameId 稳定，不用 UI 名称作为存储键 |
| 游戏阶段 | announced、test、post-test、live、retired | 与站点部署状态独立，游戏 live 不等于页面已发布 |
| 站点状态 | draft、preview、live、maintenance、retired | 未达到上线标准不进入生产导航和索引 |
| 语言 | 各 locale 的启用状态及最低正文质量 | 语言开关不能替代逐页翻译审核 |
| 能力 | 页面类型、实体类型、工具能力、路由模板 | 导航、路由和测试必须引用同一能力定义 |
| 归属 | 内容 owner、部署分组、资源命名空间 | 环境对应的服务名集中映射，不从用户输入直接拼接 |
| 运维 | 包体预算、关键页面集合、复核策略 | 数值为经确认的预算，不混同平台硬限制 |

GameManifest 保存稳定声明，不应写入不断变化的当前生产版本。实时状态存入 ReleaseRecord，避免配置文件与云状态互相覆盖。

### 6.2 ContentRecord：内容与事实

最小字段：稳定 contentId、gameId、region、contentType、slug、schemaVersion、内容版本、正文/实体数据、owner、来源列表、事实状态、语言状态。

日期语义必须分开：

- `publishedAt`：首次公开时间。
- `updatedAt`：最近一次实质内容变更，不能因定时检查而自动刷新。
- `sourceCheckedAt`：来源最后核验时间。
- `reviewDueAt`：下一次应复核时间。
- `validFrom / validUntil`：活动、兑换码等事实的有效窗口；未知必须显式标记，不填虚构日期。
- 日期使用带时区的时间格式；区服截止时间保留原始时区及归一化值。

来源建议包含官方 URL、区服、获取时间、摘要或指纹、支持的具体事实、核验者。页面引用应指向支持该结论的来源，不只是统一链接游戏官网。

语言状态建议为 `missing / draft / reviewed / published`；必要的 fallback 可以服务阅读，但不得因此自动声明为可索引的完整翻译。

### 6.3 PageManifest：可访问与可索引清单

由游戏声明和内容版本生成，记录 route、owner、locale、region、contentRevision、canonical、indexable、robotsPolicy、alternateGroup 和真实内容修改时间。

约束：

1. 同一环境和 route 只能有一个 owner，重复或未知 owner 阻断生成。
2. canonical 必须符合当前公共域名和对应内容，不能含预览域名。
3. hreflang 仅包含已就绪的有效对应页面，要求互相可达，不强行凑齐三种语言。
4. sitemap 页面集合由 indexable 状态导出，禁止重新手写游戏名单。
5. 不存在、重定向、noindex 和未就绪内容不进入目标可索引集合。

### 6.4 ReleaseRecord：发布与回滚

建议记录 releaseId、环境、输入 commit、锁文件/补丁摘要、内容版本、PageManifest 摘要、目标服务列表、候选版本、前一版本、资源版本、验证结果、审批记录和线上观测。

状态建议：

```text
planned -> validated -> preview_ready -> approved -> promoting -> verifying -> released
                       |                  |             |
                     failed            cancelled       failed -> rollback_pending -> rolled_back
```

多服务发布不假定原子性；每个目标独立记录状态。部分服务成功时，整体应明确显示 partial_failure，不得显示 released。若回滚失败，标记 needs_reconciliation，停止后续自动动作。

内容指针方案应使用条件更新或等效并发控制，避免较旧发布覆盖较新发布。无法验证当前状态时停止推广，不采用盲目重试。

## 7. SEO、路由与公共页面规范

### 7.1 Sitemap 所有权

- 根 `/sitemap.xml` 作为合法 sitemapindex，列出主站子图和游戏/分组子图；现有子图 URL 尽可能保持稳定。
- 子图使用 urlset，仅列可索引页面，不把其他 XML 当作网页提交。
- 主站子图不再重新计算已经委托给独立 owner 的页面清单。
- 保持 robots 声明有效；根图迁移须验证爬虫入口、子图可用性与旧提交兼容。
- lastmod 使用真实内容修改时间；无法提供可靠日期时宁可省略，不批量填当前日期。
- 同时校验单图 URL 数量、文件大小、XML 转义、绝对 URL 和压缩输出，接近协议上限时分片。

### 7.2 语言、状态与内部链接

- 优先修索引集合，不为消除 noindex 告警而开放未翻译页。
- 区服与语言是不同维度：英文页面不自动代表国际服事实，中文页面也不能混用其他服务器日期。
- 内部链接只由一处负责添加 locale，输出 URL 必须已经是最终规范地址，避免 `/zh/zh/`。
- `post-test` 明确显示测试结束/资料归档，不能由默认分支标记为待开服。
- 游戏不存在、内容不存在、栏目未开放应返回正确 404/410 或有根据的迁移跳转，不得用通用 200 页面掩盖。
- 删页或合并前检查访问、外链与替代内容；不对所有退休 URL 统一跳首页。

### 7.3 元数据、结构化数据与机器入口

- 页面模板统一 title、description、canonical、robots、有效 hreflang、社交分享和必要 JSON-LD。
- Article、Breadcrumb 等数据必须与可见正文一致；没有适用结构化类型不自动判为错误。
- 作者/审核者可使用真实团队身份，但不虚构专家身份、评论、评分或发布日期。
- llms.txt 以稳定目录和内容说明为主；动态版本信息引用同一事实源，不能手工长期留存旧版本描述。
- 不把 llms.txt、IndexNow 提交成功或 schema 存在当成已收录、已排名或已被 AI 引用。

## 8. 内容运营体系

### 8.1 游戏等级

| 等级 | 选择依据 | 推荐维护方式 |
|---|---|---|
| A 核心 | 实际需求、访问与可维护性，初期选择 3–5 个 | 高风险时效内容建议 24–48 小时内复核，活动期限到点自动改变展示资格 |
| B 长尾 | 有稳定检索需求、更新频率较低 | 每周或版本节点复核，优先补高价值缺口 |
| C 观察 | 预约、测试或资料尚少 | 事件驱动更新；只发布已证实信息，不提前制造完整百科规模 |
| D 归档 | 历史版本或停止维护内容 | 明确归档与适用版本，提供当前入口，保留有价值的稳定 URL |

时间为建议运营目标，不是已具备服务承诺。负责人应根据精力确认；无法维持时降级范围，不静默累积过期内容。

### 8.2 内容任务闭环

```text
发现信息 -> 判断是否与本站相关 -> 核验来源/区服/时间
        -> 与已有事实比较 -> 无实质变化：记录核验后结束
                        -> 有变化：修订 -> 审核 -> 预览 -> 发布 -> 线上验收
```

读取失败、未检查、确认无变化、确认有变化必须是不同终态。现有事实已覆盖时，不为演示系统重复生成草案。

建议同时进行的编辑批次初期限制为 1–2 个。问题诊断应有时间盒和退出条件，不继续无限产生独立实验与验收副本。

### 8.3 新游戏最小上线包

- 明确负责人、区服、运营等级和资料来源。
- 先完成约 5–15 个有真实信息价值的页面：状态、官方入口、新手问题、核心系统、来源说明等。
- 只开放已达到正文质量的语言和栏目。
- 首页、列表、详情、404、站内入口、搜索、sitemap、移动阅读及至少一个核心操作通过。
- 无虚构的上线日期、兑换码、数值、奖励和官方结论；不确定信息需明确说明。
- 有内容版本、发布记录、已验证回滚路径和下一次复核安排。

### 8.4 已有内容治理

先选择前 100 个高访问或高风险页面建立台账；没有访问数据时，按首页入口、当前版本、下载、奖励和核心工具确定临时优先级，并注明依据。

对偏离玩家意图的运营/产品建议文章，先核查实际查询和价值，再决定独立 editorial 分类、重写、合并或不索引；不批量删除所有既有 URL。

原神缺译等问题先收紧索引资格，再按需求补翻译，不把一次性翻译几百篇作为第一阶段依赖。

## 9. 发布与 CI/CD 规范

### 9.1 统一发布体验

第一版可使用已有脚本和清单输出，不强制先开发新后台。维护者需要看到：

- 改了什么、影响哪些游戏和服务；未知影响明确标注。
- 将进入哪个环境，是否会改变生产流量。
- 校验是否完成，预览对应哪个不可变版本。
- 当前线上、候选、可回滚版本，以及尚未核实的状态。
- 审批后的推广顺序、观察项和失败停止策略。

### 9.2 发布门禁

1. 生产目标服务白名单与环境映射必须结构化验证，禁止凭文件 includes/命令名称确认。
2. 预览环境与生产隔离；预览发布不能使用默认生产环境，预览页面不得进入生产 sitemap。
3. 同一发布尽量构建一次、推广同一摘要。若环境变量会改变构建输出，必须声明例外、分别校验，不能假称同一产物。
4. 跨服务变化先发布兼容的下游内容和资源，再切 Router/清单；旧消费者要能读取过渡期格式。
5. Router、内容与资源有联合兼容记录；发生部分失败时使用预定回滚顺序，不能随意对所有服务逐一回退。
6. 线上验收包含正文/版本、索引、静态资源、关键导航和 API 边界，不能只检查 HTTP 200。
7. 上传不等于发布，切流不等于验收，完成状态必须有实际观测。

### 9.3 变更影响矩阵

| 变更类别 | 最小验证范围 | 默认发布范围 |
|---|---|---|
| 单游戏普通内容 | schema、来源/日期、镜像、语言、PageManifest、关联页预览 | 该内容版本及明确的跨游戏派生物 |
| 单游戏专属模板 | 该游戏完整页面族、资源、语言、功能回归 | 该游戏所属部署单元 |
| 跨游戏摘要/搜索 | 所有消费者与样例结果 | 相关索引或平台服务 |
| 共享模板、core、Router | 受影响全部游戏；无法证明范围则全量 | 明确列出的相关服务 |
| 锁文件、运行时、补丁、构建配置 | 全量类型/测试/构建、包体与运行时回归 | 经审批的服务集合 |
| 纯文档 | 文档链接与格式校验 | 不需要生产发布 |

现有流水线不一定已经实现此矩阵。尤其文档提交仍可能触发既有自动验证；不能把建议误当当前配置。Git 交付前应重新确认自动触发范围，不为文档主动触发生产流程。

### 9.4 包体与构建成本

- 按部署单元记录 gzip 包体、构建时长、启动/CPU 与资源数量。
- 硬上限取已核实套餐与平台限制；内部预算留出增长余量。
- 历史 2.2 MiB 预算与已观察主站体积冲突，应先确认并建立降载计划，而非直接启用使当前主干永远失败的门禁。
- 过渡期可采用“已知基线登记 + 禁止无批准继续增长 + 分阶段达标”，硬平台限制不可豁免。
- 自定义 Next 补丁列为运行时风险：固定锁文件、校验补丁生效、维护升级回归用例和退出路径，不混入内容治理批次升级。

## 10. 安全、性能与可观测性

### 10.1 安全边界

- 不把生产凭据写入 manifest、报告、浏览器或构建产物；按环境最小权限使用。
- 公共内容审计不访问或修改真实用户数据，不把认证可用性等同真实 OAuth 已验收。
- 所有内容渲染遵循统一脚本注入、外链和 JSON-LD 转义策略；新增来源适配器应限制目标域名、重定向、响应大小与超时。
- 统一主站与独立应用的基础响应头；CSP 如需新增，先报告/兼容验证，避免直接阻断地图、登录或必要资源。
- 私有 API 保持不缓存，用户状态不混入公共 HTML；会话与内容缓存测试分开。
- 备份恢复不得绕过账号删除记录。生产删除清单与恢复后重放方案尚未实施，应继续独立治理，不因本项目声称已满足全部隐私要求。

### 10.2 性能治理

当前独立游戏 HTML no-store 有避免旧 HTML 引用失效资源的背景。恢复缓存的前提是不可变资产、旧资源保留、版本兼容及受控失效，而不是删除一个响应头。

试点按页面类型记录：HTML 解压体积、实际传输字节、JS、首屏图片、请求量、分地域 TTFB、缓存命中与真实用户指标。审计观察到洛克国服角色列表 HTML 约 670 KB、262 个图片元素，可优先验证分页、摘要数据和按需加载；这不直接证明 CWV 不合格。

后续可采用 LCP p75 ≤ 2.5 秒、INP p75 ≤ 200 毫秒、CLS p75 ≤ 0.1 作为体验目标；必须明确实验室数据与真实用户数据的差别。无样本标为不足，不填“通过”。

### 10.3 指标与告警

| 指标 | 建议目标或动作 | 数据来源 |
|---|---|---|
| sitemap 合约 | 提交集 100% 满足 owner/语言/索引规则 | 生成校验 + 线上核验 |
| 内容派生物漂移 | 0；出现则阻断关联发布 | 版本与哈希对账 |
| 核心时效内容逾期 | 目标 0；逾期降级展示并进入复核队列 | 内容元数据 |
| 发布状态 | partial_failure 不得关闭任务 | 发布记录与线上版本 |
| 构建与包体 | 每次记录，超批准预算阻断或进入已批准例外 | CI 制品 |
| 运营效果 | 分游戏非品牌点击、有效页、工具使用与维护工时 | 经授权的 GSC/分析 + 工时记录 |
| 磁盘增长 | 天数与容量双上限；保护项优先于自动回收 | 本地清单与引用检查 |

监控设计不是本次创建定时任务的授权。后续告警仅在有意义变化、失败或需要人处理时通知，避免持续无变化消息。

## 11. 存储、备份与清理规范

### 11.1 容量基线

| 目录类别 | 审计占用 | 处理原则 |
|---|---:|---|
| 历史 build-attempts | 2.778 GiB、61 个目录 | 混有源码、证据、状态，先分类保护后归档 |
| 5 应用 .next/.open-next | 约 1.489 GiB | 可再生；确认当前验收/回滚依赖后才可回收 |
| 根 node_modules | 1.111 GiB | 可重装，不作为日常反复清理目标 |
| reports | 416 MiB、902 个文件 | 证据分类、压缩、去重，未跟踪不等于垃圾 |
| .turbo | 255 MiB | 可再生缓存，受容量与年龄策略管理 |
| .git | 117 MiB | 版本历史，禁止当缓存删除 |

上述主要类别互不重复；约 1.738 GiB 缓存候选由五应用构建产物、根 .turbo 和根 .next 构成。历史图片重复逻辑字节约 1.245 GiB 已包含于历史目录，不能相加计算保证回收量。APFS 克隆、压缩和硬链接也会影响真实释放空间。

### 11.2 四类存储边界

1. 源码与内容源：版本控制，保留可追溯历史。
2. 可再生缓存：可清理、可重建，不作为唯一发布证据。
3. 持久业务数据：工作台数据库、事实、审核、用户数据，单独备份和权限管理。
4. 发布与审计证据：输入摘要、版本、验收、回滚与未结案问题，按用途保留。

历史构建不应重复复制所有游戏图片和依赖。优先引用固定 commit/锁文件/补丁及内容哈希，公共素材内容寻址复用；不可变输入与可写工作区隔离，防止共享硬链接被编辑污染。

### 11.3 建议保留政策

| 对象 | 初始建议 | 保护例外 |
|---|---|---|
| 普通失败实验 | 7 天 | 未结案故障、安全或审核证据 |
| 普通成功实验 | 14 天，每游戏最多 2 份 | 正在验收、关联候选发布 |
| 正式发布产物 | 至少当前版、前一可回滚版，兼容期内更多版本 | 不以数量规则删除仍被引用资源 |
| 重复详细日志/清单 | 摘要常驻，完整内容压缩归档 | 需要完整审计链的批次 |
| 日常数据库与备份 | 单独制定业务保留期 | 不套用缓存 TTL；首份及最近验证备份保护 |

这些是待批准的起始值，不是已启用政策。旧资产保留期还需覆盖 HTML 缓存寿命、在途会话和回滚窗口，不能只固定“保留两版”。

### 11.4 清理安全门禁

- 默认仅预演，输出路径、实际解析路径、字节、分类、引用、保护理由、活跃状态和建议。
- 不允许以 untracked、旧修改时间、old 文件名推断可删除。
- 扫描不完整、引用无法解析、活动状态不明时保护候选，不冒险继续。
- 阻止越出允许根目录的符号链接、挂载点与路径替换；执行前再次核验清单摘要和占用，减少检查到执行之间的变化风险。
- 管理型 Git 工作区通过其管理工具处理，不用普通递归删除破坏注册关系。
- 删除需另行批准；没有备份的不可再生数据不列为普通缓存。
- 清理后核验保留物完整性与实际可用空间；隔离移动本身不等于释放磁盘。

### 11.5 备份与恢复

工作台日常数据库与 build-attempts 必须分开。统一现有“备份整个目录”与“不默认备份历史构建”的文档歧义。采用受支持的 SQLite 一致性快照，或停写后处理数据库及实际存在的 WAL/SHM，不混合不同时间点文件。

恢复演练优先新目录/测试环境，验证 schema、完整性、关联记录与应用读取，再决定真实切换。RPO/RTO 在恢复实测和业务需求确认后制定，不把一次文件复制通过当成完整灾备。涉及用户数据时还须验证删除记录重放和访问控制。

## 12. 测试与总体验收

| 测试层 | 必测内容 | 失败处理 |
|---|---|---|
| 合约单测 | 游戏声明、内容日期/区服、语言、owner、环境映射、索引决策 | 阻断关联生成和发布 |
| 集成 | 源到公开镜像/搜索/PageManifest 的版本一致、构建输入可追溯 | 漂移不得人工忽略 |
| Worker 边界 | 真实路由、查询参数、资源前缀、API 归属、预览隔离、404 | 不扩大生产切换 |
| SEO | XML 类型、提交集合、canonical、noindex、hreflang、正文语言 | 不以移除保护策略掩盖失败 |
| 浏览器 | 桌面与 390px 手机、跨 Worker 导航、返回、搜索、核心工具 | 区分环境故障与产品回归 |
| 发布故障注入 | 上传失败、部分推广、并发发布、过期审批、回滚失败 | 正确停止并显示真实状态 |
| 存储 | 活动目录、符号链接、保护引用、过期候选、快照恢复 | 默认不删、隔离演练 |
| 性能 | 同地点/设备/缓存条件下比较基线与候选 | 不用单次 TTFB 代表全球表现 |

验收证据最小集合：固定输入、执行命令/范围、通过/失败/跳过、产物摘要、目标环境、线上观测、回滚证据、未覆盖项。不得让大量重复截图和完整目录清单替代关键结论。

全局完成定义：

- [ ] 已确认问题有回归测试，并在相应层验证，而非只改源码。
- [ ] 试点游戏从录入、审核、预览、发布到线上验收与回滚形成完整路径。
- [ ] 新游戏标准接入不新增专属基础设施；例外有记录。
- [ ] SEO 和派生数据合约一致，原公共 URL 保持兼容。
- [ ] 发布者无需人工判断多个 Worker 的实际更新状态。
- [ ] 存储政策可预演、可保护、可审计；未批准前不执行删除。
- [ ] 实际收益有基线对照，未知与未覆盖事项明确列出。

## 13. 迁移、回滚与风险

### 13.1 迁移顺序

1. 固定新的实施基线，隔离当前脏工作区与实验文件；不 reset/pull 覆盖既有内容。
2. 先堵发布环境混用风险，再统一试点页面的事实与索引契约。
3. 新清单先影子生成，与旧输出比对；差异逐项说明，不静默接管全部页面。
4. 选一款低复杂度但有真实维护需求的游戏，完成从内容到生产验收的纵向试点。
5. 保持旧 URL，逐步切换 owner 或内容读取方式；一次只扩大一个已验证边界。
6. 完成观察与回滚演练后，才考虑删除旧实现、缩减服务或扩大接入。

### 13.2 风险与对策

| 风险 | 对策 |
|---|---|
| 合并后包体超限 | 先量测依赖组成与套餐，试点分组，不直接相加各 gzip 推算结果 |
| 共享模板扩大故障范围 | 代表游戏矩阵、分组发布、兼容旧内容 schema |
| SEO 切换造成遗漏或错误语言收录 | 新旧集合差分、URL 保持稳定、按 owner 核验 |
| 内容回滚与代码不兼容 | 记录 schema/renderer 兼容区间，联合验证回滚组合 |
| 新旧资源交叉导致水合/资源失败 | 不可变资源版本、旧资源保留、跨 Worker 导航回归 |
| 清理误删唯一证据或业务数据 | 默认预演、引用保护、独立备份、批准后执行 |
| 继续建设过度复杂的工作台 | 每个功能绑定真实运营任务与节省步骤，设范围和退出条件 |
| 并发任务修改脏工作区 | 固定隔离基线、限定文件与交付范围，不把未跟踪实验纳入默认测试 |
| 自动触发消耗 Actions 或写云端 | 每批核对触发链和预算，相关变更合并一次验证，不重复试生产 |

## 14. 交付节奏与决策清单

建议窗口为 0–2 周修确定风险，2–6 周完成配置/内容试点，6–12 周依据实测决定内容发布解耦与部署分组。这是相对排期，不是确定人天或上线承诺。每阶段必须通过退出标准才能进入下一阶段。

具体纵向工作包、依赖、演示、验收及回退方式见[配套实施计划](../plans/multi-game-long-term-delivery-2026-10-23.md)。

实施前待确认：

- 第一款试点游戏与核心运营游戏名单，选择依据是维护需求而非现有 Worker 数量。
- 当前生产服务/版本、实际套餐、构建额度和可接受成本。
- 哪些内容是权威源，剩余 3 对漂移的事实/区服/版本审核；已归并的 3 对仍需独立维护事实复核日期。
- 当前可接受的人工发布步骤、审核职责和生产审批方式。
- GSC/分析数据是否允许接入；未接入时使用哪些临时优先级。
- 历史证据保留要求、数据库备份策略及允许清理的范围。
- 首批纳入范围与验收负责人；单人项目可以兼任角色，但生产审批边界保持明确。

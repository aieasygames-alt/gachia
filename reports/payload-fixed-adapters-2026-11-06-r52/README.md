# R52：固定请求组合与失败输出封堵

继续第一阶段的连续更新链路。本轮没有真实云写入、CMS 安装、数据库编辑或生产来源接续；推广与恢复 CLI 继续只开放 audit。

## 修改

- 修复固定 source advance/baseline 的最终执行器完整性检查失败后，协议已生成的来源索引或下一批交接仍可能被消费的问题。现在保留 `failure.json`；真实 reader 拒绝该目录，重跑不能覆盖输出。
- 来源、下一批读取/准备和恢复入口在第一个异步边界前复制请求。后续 pin 校验、准备及返回收据不再复用调用方可变对象；隔离覆盖验证期间替换 publication、handoff、expectations、history、network pin 的情形。
- 抽出可复用的真实推广协议完成态 fixture，保留原 27 项完成态 reader 测试，并组合合成五 owner、115 来源、90 公开对。临时证据全部位于测试自己的目录，结束自动清理，没有复制真实多 GiB 冻结构建。
- 新增独立进程固定适配器测试。测试加载器只在子进程中访问私有恢复函数；不新增生产导出、请求参数、环境跳过开关或 CLI 写入口。测试子进程清除父测试 runner 的内部上下文，并检查实际测试输出，防止空运行被误记为通过。

## 验证边界

43 项隔离组合覆盖：固定请求→真实完成态 reader→来源索引→新鲜下一批→真实本地候选/恢复准备；新 A 完整消费、五 owner 保持、精确候选运行模块、90 公开对、各层 CI 必要步骤、过期/篡改/拓扑/HTTP 失败、最终执行器失败及请求对象变化。私有恢复组合运行真实模块重验、恢复预览、journal、部署写入器和公网验证；成功只写一次，丢响应和公网失败停止，不自动重试。即使模拟已知候选再次活动，也因已有 recovery journal 拒绝第二次写入。

本测试**替换历史发布入口、执行器工作区检查、云拓扑与构建验证边界**，GitHub/Cloudflare/公网通过合成响应隔离；本地准备器实际执行 HTTP，但由小型 loopback server 代替 OpenNext。模块、renewal、部署响应、完成态和公网历史证据、来源与准备器本体均真实重读。它证明固定组合按既定边界接线及失败语义，不证明无替换的完整生产资格、真实 Cloudflare 写入或全部内容类型可发布。

本机最终结果见 [verification.json](verification.json)：CMS 346/346（含独立进程入口），独立组合 43/43，发布工具 1,479/1,479（187 + 988 + 304），Python 56/56，文档/范围 38/38，CMS TypeScript 和 whitespace 检查通过。完整套件运行于 Node 25.9.0，组合入口和 43 项子进程另外在本机 Node 22.22.2 通过；后者仅是兼容性附加检查，不冒充 CI 指定的 Node 22.23.4 或部署运行时。

本提交的精确完整 CI 必须在提交后单独执行并重验，结果由 `verify-exact-ci.mjs` 写入独立的 `ci-exact.json`；实现检查点不提前记录通过，旧 R51 完整 CI 不覆盖本轮代码。

## 剩余开发

正式生产验证器和历史发布 reader 仍只接旧 `unified_observed_source_handoff`。新 `unified_next_batch_baseline` 可读、可编译、可本地准备，但尚不能用于下一次正式上传。应先接通这个合同及后续历史/恢复读取，补固定全链路资格，再取得新执行器精确完整 CI、新鲜续验、首批推广、全公网接受、实际来源接续与下一批正式验证。第一阶段尚未关闭，第 2 至 5 项仍待执行。

本轮没有扩大 Ananta 中文安装清单单条试点资格，没有重新要求内容来源认证；账号关闭、IndexNow 暂停、公众服务独立于 CMS 的约束不变。

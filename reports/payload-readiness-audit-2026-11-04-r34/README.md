## 2. 主要发现

### F1 [P1] 同游戏hold/撤回后的后续候选会隐式恢复导入O

- `services/content-cms/src/desktop-export.ts:8`：输出从Git/导入O克隆，再覆盖传入的合格记录。
- `services/content-cms/scripts/desktop-content.ts:53`：正式导出只传published且hold=false的记录。此前已上线、随后hold或撤回的记录被排除。
- `scripts/desktop-publish.mjs:70`：候选/changed清单仍与O核对，未表达完整的当前公开A→候选B差异意图。
- `scripts/desktop-evidence-preparation.mjs:42`：A与B只要求存在文字差异，不要求每个变化都在明确批准的变更集合里。

真实函数隔离复现：先用一条合格记录生成已公开A；模拟其hold=true或_status=draft，同时批准另一条B。下一导出将A的标题恢复为O，manifest/inspectCandidate仅列B，A→B实际却变化两条；`inspectCandidate`返回`editorial_candidate`，现有非空差异条件通过。两种状态均复现，同时保留两条eligible的对照组不回退。证据为[复现源码](export-preservation.ts)与[输出](export-preservation.json)。

**这不是已经发生的线上事故**：没有改真实记录或执行云发布，本轮公开JSON与已接受内容完全一致；也未模拟完整云推广。它是已安装导出函数与现有本地候选门禁的真实缺口，不是内容事实校对问题。应列为“放心日常使用”前的首项工程修复，而非重新否认已经完成的首发。

建议先实现最小fail-closed保护：以可信当前公开A为参照，逐记录/字段核对候选变化与明确发布意图，不相关记录的隐式回退必须拒绝。再完善保留A与显式撤回/重置契约；不能简单把所有CMS草稿混入公开候选，也不能把hold等同于网站删除。回归覆盖O→A→B、hold/撤回、显式还原、全部无eligible、草稿版本、三语言、跨游戏Main保留。旧manifest/封存历史保持不变，新格式另行版本化。

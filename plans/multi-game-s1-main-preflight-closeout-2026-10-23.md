# S1.5 交付：主站发布前收口与跨 Worker 导航

日期：2026-10-23，Asia/Shanghai。分支：`codex/multi-game-s1-release-safety`。功能候选提交：`1114fb5c09704edb0e2e9e9eebf20a1500a1df71`；后续同批变更仅补充 CI 编译产物验收门禁和文档，不改变已部署的应用/静态产物。

**结论：修复三个实际发布风险，重新构建并封存主站候选，完成现有主站 staging 的限定验收。只部署主站 staging 一次；生产、四个游戏 Worker、Router 及其他 staging 未发布。此结论不是全站无条件放行，也不是主站已上线。**

## 1. 发布前发现的问题

| 问题 | 证据与影响 | 本批处理 |
|---|---|---|
| 生产验收仍要求 session 200 | 账号下线后正确响应是 404；原脚本会在部署后误判失败 | 统一源码账号策略，检查错误码、no-store/noindex 和不刷新 Cookie |
| 候选缺失线上旧 chunk | 线上主站 23 个入口资源中，最初 21 个 JS 不在 S1.4 候选里；只测新首页会遗漏旧标签页风险 | 从当前线上部署的精确不可变产物保留旧 `_next/static`，并验证线上/候选字节 |
| 主站到独立游戏可能跨构建软导航 | 实际 Router 演练中，Next 预取后请求了主站命名空间下的两个蓝色星原 chunk，产生 404；最终整页降级到目标页不能算通过 | 主站通用 Link 对独立 live game owner 输出原生锚点，关闭这类 RSC 预取；同主站 HI3 客户端导航保持 |

第一次浏览器夹具还误选了移动端隐藏的顶部同名链接，随后限定选择 `main` 内游戏卡片；这属于测试定位修正。真正的 chunk 404 在修正选择器后仍可复现，修复业务导航后才通过。未通过忽略失败脚本或仅断言最终 URL 来放宽验收。

## 2. 交付内容与长期约束

- owner 规则复用 `GAME_DEPLOYMENTS`，新游戏进入独立 live 状态时，主站链接自动使用文档导航，不再为四个游戏分别写点击补丁。主站负责的游戏/工具仍保留 next-intl/Next Link。
- 增加旧资源准备、安全提取、合并和校验工具。只读固定 GitHub 仓库的 Actions API；旧产物不得过期，必须同时关联精确 artifact ID、ZIP 摘要、成功 deploy 日志和当前线上 UUID。同 commit 的另一份 artifact 不能代替。
- 先检查路径、链接、重复、预算及不可变路径冲突，再提取/复制；不执行旧 Worker、不提取旧 HTML 或服务端缓存、不覆盖冲突资源。清单放在非公开产物目录中。
- 生产工作流新增旧 artifact ID / ZIP SHA-256 显式输入，保持 main ref、`RELEASE_MAIN_ONLY`、环境门禁、当前唯一 100% 回滚版本和单主站范围；不增加迁移或其他 Worker 发布。
- 编译产物合并旧资源后才封存。staging/production 使用同一 artifact ID 和 tar 摘要，两次部署前均重新核验保留清单。生产请求必须通过 staging 的编译后 31 HTTP / 18 浏览器 / 8 跨 owner 夹具和旧资源抽样，不能用 dev-server 测试冒充。
- 生产审计扩展为五个 owner 的页面、命名空间内 JS/CSS 及四份游戏 sitemap；固定正式域名、GET、无凭据、不跟随重定向，不创建账号或触发内容提交。

完整规范、预算上限、命令和回退边界见[主站资源保留与发布规范](../docs/main-release-static-retention.md)。测试内联 next-intl 仅用于让 Vite 解析真实的 Next 子路径和 URL 序列化，不修改 Next 补丁、锁文件或依赖版本。

**本批主站候选通过已列出的 staging 门禁，可以进入受控主站发布流程；生产发布与生产验收尚未完成。**

2. CI 会产生另一份构建产物，必须在同一次运行中封存、通过编译后 staging 验收，再将同一份产物用于生产；不能把本地 tar 摘要或本地成功结果套用到新 CI 产物。此次 CI 新门禁已在本地校验，未声称已执行真实 Actions。

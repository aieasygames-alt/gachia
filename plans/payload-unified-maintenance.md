## 长期架构决定

- **范围**：一套 Payload 管理所有游戏及地区 scope，不给每款游戏另建 CMS。小样本只是验证手段，不是最终交付范围。
- **运行边界**：CMS 独立依赖、锁文件、认证与存储。保留公众站点 Next 15.5.28 和原补丁；不接管或开启玩家账号。
- **URL 与归属**：保留公开 ID、slug、URL、别名与语言索引政策。地区与语言分别建模；游戏不等于 Worker，Router 与路径级所有权初期保留。
- **模型**：Game/Region、类型化内容、Translation、SourceEvidence、Review/Hold、Media、ContentBatch、Snapshot、ReleaseMap、JobRun。当前实验模型只验证基础能力，不是最终通用 JSON 表设计。
- **权威源**：每个迁移单元有唯一编辑源。接管前旧来源权威，接管后 CMS 权威；禁止永久双向同步。
- **发布边界**：Payload 的 published 只是编辑状态；网站只读经批准的不可变公开快照。证据、草稿、账号信息不进入公开资产。
- **日常维护**：长期目标是内容发布不依赖 Worker 重建。为尽快可用，首个 guides 交接先复用旧数据消费和封存 Worker 发布流程，仅从本机执行；尚未完成，不把候选导出当公开发布。
- **已决与待决**：编辑端为本机 Node + PostgreSQL + 私有媒体，公众站点仍在 Cloudflare；不使用 Tunnel。首发双 owner 发布执行器已安装，真实云验收、通用公众激活协调器及完整版本缓存协议仍待交付。

用户故事：U1 全游戏统一管理；U2 日常更新；U3 新增游戏；U4 多 Worker 一致发布；U5 持续维护和恢复。

完整剩余任务定义保留 R8 的 T01–T12 表，执行状态以 `project-task-status-current.md` 的R28权威节和V1有限计划为准。当前双游戏来源已登记且重选通过，普通成功发布接续/跨游戏Main重绑定/本地准备编排及已知完整兼容恢复来源接续已实现安装；首次无来源或外部未知版本继续拒绝。独立密钥托管/跨机验收保留明确待办，真实编辑出现即优先云验收，再逐范围接管。源码ZIP不是正式Git提交，私有R2密文往返也不等于整机丢失后可恢复。云自动发布入口保持关闭；事实校对/缺译/命名差异后置。不把本机后台或合成 RSC 验收当公众接管，不公开草稿或未经授权的媒体。

## 历史：最初实验批次的允许动作、失败停止与回退

本节仅记录最初隔离实验政策，**不是当前授权状态**。用户后来决定本机部署、仅本机发布并给予所需操作默认授权，已有本机安装、R2异地密文和Git/CI实际执行证据。当前任务仍须按范围与副作用判断，不能以默认授权制造编辑、批准第三方媒体或跳过生产证据；R19审计本身没有云写入。

- 允许：隔离工作树、本地依赖安装、本地临时数据库、合成数据测试、只读源码清单、文档更新。
- 不允许：创建云资源、使用生产 DB/R2、部署/切流、清缓存、开启玩家账号、推送或触发 Actions。
- 依赖不兼容、锁文件跨到主站、数据库路径/凭据指向远端、外部工作树出现非本轮改动时立即停止相应动作并说明。
- 本批没有网站切换；停止本地进程即可回到原运行状态。保留隔离工作树和日志，不覆盖原脏目录，不自动清理用户数据。
